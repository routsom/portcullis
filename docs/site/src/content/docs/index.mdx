**portcullis** sits between agent clients and tool servers and provides identity,
authorization, sandboxed execution, auditing, and protocol translation — without
adding meaningful latency, without an enterprise paywall, and **without ever
executing tool logic in its own process**.

## Why portcullis

<CardGrid>
  <Card title="Nothing executes in the gateway" icon="star">
    The edge parses, decides, routes, and logs. Tools run in a separate,
    sandboxed process (uid, seccomp, landlock, no network). A prompt injection
    can't turn the gateway into a shell — there is none.
  </Card>
  <Card title="All Apache-2.0, no enterprise tier" icon="approve-check">
    SSO, RBAC, DLP, audit, rate limiting, and multi-tenancy are core features. A
    build-time check enforces that nothing is gated on a licence.
  </Card>
  <Card title="Latency is a hard budget" icon="rocket">
    p99 ≤ 5 ms of gateway-added overhead, gated in CI. The passthrough path never
    fully deserializes payloads.
  </Card>
  <Card title="Zero required infrastructure" icon="setting">
    One binary runs on a laptop and in production. Postgres, Redis, Vault, and
    OIDC are optional integrations, never prerequisites.
  </Card>
</CardGrid>

:::caution[A note on trust]
portcullis is security-critical infrastructure. The Linux sandbox is verified in
CI on a real kernel, not on a developer's laptop, and — like any gateway fronting
untrusted tools — should pass an independent security review before you rely on
it in production. The [security model](/portcullis/security/model/) states plainly
what is enforced and what is not yet.
:::
